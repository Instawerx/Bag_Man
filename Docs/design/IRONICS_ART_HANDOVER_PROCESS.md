# IRONICS — Art Handover Process (LAW)

**Operator ruling, 2026-08-10.** Every new art asset goes through this process. No exceptions, no
"just this once for a placeholder" — a placeholder that ships is indistinguishable from art nobody
reviewed, and the whole point of a locked style system is that nothing enters the game that has not been
measured against it.

> **THE RULE IN ONE LINE:** new art is **briefed from the locked SSOT + an existing Artifact**, routed to
> **the right producer for its family** (§2 Step 4 — `/design` for component art, *not* for pictorial
> art), and **reviewed back against the same SSOT** before it lands.

---

## 1. WHY A PROCESS AND NOT JUST GOOD TASTE

The art system is already **locked** — `IRONICS_UI_STYLE_SSOT.md` §1 brand, §2 palette, §3 panel system,
§4 typography (ruled 2026-08-10), §6 component tokens. The failure this process prevents is not ugly art;
it is **art that is individually fine and collectively inconsistent**, which is how a game stops reading
as AAA. That drift arrives one reasonable-looking asset at a time, and each one is defensible on its own.

Two things this project has already learned the hard way, both of which this process encodes:

- **The palette has been swept once already.** §2.6 records the cyan → electric-blue migration as a
  *cross-inheritance LAW*, because a colour introduced off-system propagates into everything that
  inherits from it and the cost is a sweep, not a fix.
- **A stand-in becomes the shipping face if nobody rules it.** §4 exists because the mockups' type stack
  was about to be inherited into the product by default. It took an explicit ruling to stop that.

## 2. THE PROCESS

### Step 1 — Cite the lock, do not restate it

Open `IRONICS_UI_STYLE_SSOT.md` and pull the sections the asset actually touches. **Cite them; never
paraphrase.** A brief that restates a token is a second copy of that token, and the second copy is the one
that goes stale.

### Step 2 — Name the reference Artifact

Every brief points at an existing Artifact so the new asset has something to be consistent *with*:

| Artifact | What it establishes |
|---|---|
| `Docs/design/IRONICS_Home_Screen_Mockup.html` | The root surface: door composition, footer, chrome density |
| `Docs/design/IRONICS_League_Door_Mockup.html` | The free-side lobby: row density, calm treatment |
| `Docs/design/IRONICS_Staked_Door_Mockup.html` | The staked lobby: the stake axis, the denomination strip |
| `Docs/design/IRONICS_Lobby_Mockup.html` | Shared lobby chassis and the five pinned regions |
| `Docs/reference/IRONICS_Styling_Sample.html` | The glass/neon treatment at component scale |
| `Docs/reference/IRONICS_BOLT_Assets.html` | The bolt/identity marks |
| `Docs/reference/IRONICS_Tier2_Concepts.html` | Secondary concept language |

### Step 3 — Write the handover prompt

One file per asset family, in `Docs/design/handovers/`. The template is §4 below. It must be
self-contained: someone reading only the handover should be able to produce the asset without asking a
question, because the questions are what produce drift.

### Step 4 — Route it to the RIGHT producer

⚠ **CORRECTED 2026-08-10. This step originally said "hand it to `/design`" for everything, and that is
wrong.** `/design` (claude.ai/design, reached by the `DesignSync` tool) reads and writes **design-system
projects** — component libraries, HTML previews, tokens, prop contracts. **It has no image generation.**
Sending a key-art brief there produces nothing, and the error was mine: I wrote the step before checking
what the tool actually does.

**Art divides into two families with two different producers, and the brief must name which:**

| Family | Examples | Producer |
|---|---|---|
| **UI / component art** | Component previews, token swatches, style specs, anything that is markup | **`/design`** via `DesignSync` — the `design-sync` skill covers the flow |
| **Pictorial art** | Key art, concept art, textures, illustrations, marks, tile imagery | **NOT `/design`.** See below — ⚠ the canonical producer is operator-owed |

⚠ **THE PICTORIAL PRODUCER IS NOT YET RULED, AND UNTIL IT IS, A BRIEF SITS IN `handovers/` UNSENT.**
That is a real state and it is better than guessing: a brief in the repo is reviewable and re-routable;
an asset generated by the wrong pipeline is a stand-in that ships. Candidates on hand, none confirmed:

- **The AgentIntegrationKit bridge's `GenerateImage`** — in-editor, lands assets directly in the project.
  Closest fit for texture-shaped work; unverified for key-art quality at 2560 × 1440.
- **The Rodin Gen-2.5 pipeline** (`reference-rodin-gen-pipeline`) — replaced Tripo 2026-07-28 and is the
  project's established genAI path, but it is a **mesh** generator. Probably not the right tool for 2D.
- **A human artist**, with the brief as the commission.

**Rule until it is ruled:** write the brief, commit it to `handovers/`, and record it in §6 as **unsent**.
Do not improvise a producer. If a brief turns out to be insufficient once it does reach one, fix the
brief and re-run — that is how the next asset in the family benefits.

### Step 5 — Review back against the SSOT, then land

Check the returned asset against the *cited* sections, not against taste. The checklist is §5. An asset
that fails goes back with the failing clause quoted; it does not get "adjusted in engine".

⚠ **The engine side is built to wait.** Every art slot in the front end is a soft pointer that renders
*nothing* when unset — `UAFLW_VenueShowcase::ApplyDetail` hides the image rather than leaving the previous
venue's art under a new venue's name. **An empty slot is a correct state, and it is always better than a
stand-in.** Nothing is blocked on art arriving; nothing should ever be unblocked by inventing it.

## 3. WHAT COUNTS AS "NEW ART"

Anything a player sees that is not generated by the token compiler: key art, illustrations, icons,
concept-derived textures, marks, backgrounds, tile imagery.

**Not covered:** brushes, colours, radii, blurs and type faces. Those come from
`Source/LyraEditor/AFL/AFLTokenCompiler.cpp` and are changed by editing tokens, never by drawing.

---

## 4. HANDOVER TEMPLATE

```markdown
# HANDOVER — <asset family>

## What and where
<what the asset is, which surface consumes it, which C++ property it lands in, and the exact
asset path it will occupy>

## Reference Artifact
<file from the §2 table, and what specifically to take from it>

## Locked constraints — cited, not restated
- Palette: IRONICS_UI_STYLE_SSOT.md §2.1 <name the tokens in play>
- Panels:  §3 <the glass treatment and blur band, if the art sits behind glass>
- Blend:   §2.3 + the BLEND RULE <Electric = core/fill/active; Violet = rim/edge/focus,
           never touching readable core, fill or text; rim is size-gated ON at ≥64px>
- Type:    §4 <only if the asset carries type at all — prefer that it does not>

## Composition
<framing, safe area, focal point, where UI will overlay it>

## Deliverables
<count, dimensions, format, naming>

## What this asset must NOT do
<the negative spec — usually the most useful section>
```

---

## 5. REVIEW CHECKLIST

- [ ] Every colour traces to §2.1 / §2.2. No new hues.
- [ ] **The BLEND RULE holds:** Electric is core/fill/active; Violet is rim/edge/focus only and never
      touches readable core, fill or text.
- [ ] The rim is **size-gated** — on at ≥64px, core-dominant at ≤32px.
- [ ] Contrast survives the §2.4 readability law where the asset sits under UI.
- [ ] Geometry matches the §3 radius bands where the asset meets a panel.
- [ ] No type baked into the art unless the brief asked for it (§4 owns type).
- [ ] It reads as the same game as its reference Artifact at a glance, at thumbnail size.
- [ ] Naming follows the project prefix rule (`BagMan_` / `T_` per the surrounding folder).
