## B. Executive summary (architect)

PROPOSAL (nothing here is decided). IRONICS already owns the institutional-grade SHAPE for an admin surface: a KMS-signed session on one identity, an allowlist read per request with fail-closed semantics, adminHandler as the only way an admin Lambda exists, per-route IAM grants asserted from the synthesized template, and an audit table that is append-only at IAM. What it lacks is exactly the three things the operator named: (1) a ROLE dimension and a second factor — today one flat row can mint currency and rewrite the PlayFab catalog with a player-grade 30-minute JWT, and the same JWT is accepted as a game-client Bearer; (2) any wallet/economy surface — PlayFab is the balance of record but nobody holds a ledger of record (earn grants and Volts mints leave a 24-hour dedupe row, rake never accumulates, the portal Lambda transitively holds the full game-server money key); (3) honest metrics and controls — the only download metric counts portal page views, install/first-match never fire, 'testers' has no writer, every lever (release pointer, FlexMatch cells, kill switch) is a hand AWS CLI call with no audit row. Live checks today (read-only, account 302659227808): the admin seed DID run (IronicsAdmins = 1 row, the operator, 2026-08-25), the IAM user has NO MFA device, and there are ZERO CloudTrail trails — so the out-of-band DynamoDB write path bypasses every guard and leaves no durable record. RECOMMENDATION: build on the existing stack only — roles as permission bundles on the existing IronicsAdmins row + `requires` on RouteSpec cross-checked by the existing enumeration tests; a 15-minute admin-audience elevation token minted after Cloudflare Access Independent MFA (free ≤50 users) verified on ONE elevate route; a dedicated portal→tentpole admin HMAC key with an actor field; an append-only money journal before any money lever; a first-party events table + roll-ups as the system of record for /admin with PostHog as a confirm-or-defer second sink; SSM flags and pointer-only release routes; CloudTrail data events + 6-8 alarms. Console stays at ironics.org/admin in an isolated route group built so the apps/crm move is a folder move. Everything else (second identity store, API proxying without an origin lock, Retool/Cognito/Auth0, QuickSight, policy engines, SIEM) is named as consciously deferred. Totals for everything recommended: ≈60-90 engineer-days across four phases (≈17-24 days for the Phase 0+1 MVP), ≈$5-15/month incremental at beta scale, zero new vendors. Every new screen goes to a 1:1 mockup for operator approval before a route is wired to it (CLAUDE.md doctrine 7).

## I. Adversarial review - verdict **sound-with-fixes**

### Attacks (18)

**1. [BLOCKER] Phase 0 hygiene / today_baseline -- 'MFA device on IAM user Lead_Developer_Ironics' as the fix for the out-of-band path**  
Problem: The trust root the whole scope sits on is one IAM user with AdministratorAccess (live 2026-09-06: group IRONICS carries arn:aws:iam::aws:policy/AdministratorAccess plus 10 other broad policies incl. AdministratorAccess-Amplify/ElasticBeanstalk/AccountManagementFromVercel), ONE long-lived access key ***REMOVED-AWS-KEY-ID (rotated; see Secrets Manager)*** created 2026-06-12 (86 days, never rotated), no MFA device, zero CloudTrail trails. A console MFA device does nothing for API calls made with that key. With it, every guard the scope builds is bypassable in one call: `kms:Sign` on alias/ironics-portal-session (key policy = root kms:* only, verified live) forges any session JWT AND the proposed admin-audience elevation token (same key); `lambda:UpdateFunctionCode` on AdminApproveClaimFn / currency-earn rewrites the guard; `secretsmanager:GetSecretValue` on bagman/playfab/secret reads the title key directly; `dynamodb:DeleteResourcePolicy` + `DeleteItem` edits the 'append-only' audit log. The scope's aws:MultiFactorAuthPresent condition covers only 'human DynamoDB writes to IronicsAdmins/IronicsAuditLog', i.e. the least dangerous of these.  
Fix: Make Phase 0 item 1 the credential, not the device: (a) attach an identity-based DENY-all-unless-MFA policy to group IRONICS (`Deny * where BoolIfExists aws:MultiFactorAuthPresent=false`, carve-outs for iam:ListMFADevices/EnableMFADevice/sts:GetSessionToken) so the access key only works inside an `aws sts get-session-token --serial-number --token-code` session -- 0.25 day, $0; (b) rotate the 86-day key and set a 90-day rotation runbook; (c) strip the unrelated policies (Amplify, Beanstalk, Vercel, AIDevOps*) from the group; (d) CloudTrail management trail (free) + metric filters + alarms on kms:Sign, lambda:UpdateFunctionCode, secretsmanager:GetSecretValue on the two money secrets, dynamodb:DeleteResourcePolicy/DeleteTable from any non-Lambda principal -- detect, since an admin principal cannot be prevented from these without SCPs; (e) state in the scope that IAM Identity Center (free) with short-lived credentials is the medium-term replacement for the key. Until (a) lands, no admin-console hardening changes the actual security posture.

**2. [MAJOR] Must-have 4 Option A (console at ironics.org/admin) + Must-have 1 step-up claim 'second factor enforced at the API on the elevate ceremony'**  
Problem: Under Option A the console shares an origin with the marketing site (CursorTrail, 3D, forms, no CSP today -- grep 0 hits). Cloudflare Access injects Cf-Access-Jwt-Assertion automatically for every request under the app path while the Access session lives (1-4 h per the scope; Independent MFA doc: 'this determines how long a user can log in to Access without being prompted for MFA again'), and ironics_session is a same-site cookie (http.ts:34 SameSite=Lax, Domain=.ironics.org). So any script executing on any ironics.org page during an Access session can POST to the elevate handler, receive ironics_admin, and drive /v1/admin/* with credentials:include. The Origin/JSON-content-type checks the scope adds block CROSS-origin callers only; they cannot distinguish same-origin XSS from the console. The second factor is therefore on the Access SESSION, not on the elevate ceremony, and the 15-min elevation TTL buys little against XSS.  
Fix: Either (1) choose Option B now (admin.ironics.org, +3-5 days as the scope already prices): a separate origin makes the Origin + JSON checks effective against marketing-site XSS, CORS can then list exactly the admin origin, and the 180 KB budget coupling disappears; or (2) keep Option A but make elevate require a per-request user gesture XSS cannot forge -- WebAuthn user-presence assertion (@simplewebauthn/server, the scope's own alternative, +3-4 days) verified in the elevate Lambda -- and set the Access authentication duration to its minimum. Rewrite the security-baseline sentence to say what is true: 'the second factor is enforced per Access session; per-elevate presence requires WebAuthn'. Ship CSP nonce/strict-dynamic in Phase 0 regardless.

**3. [MAJOR] Must-have 1 elevate route: 'verifies [the Access assertion] against <team>.cloudflareaccess.com/cdn-cgi/access/certs with the app's aud tag AND requires a valid session'**  
Problem: Nothing binds the Access identity to the admin row. The assertion carries email/sub (Cloudflare application-token doc), the session carries accountId, and the scope checks each independently. Consequences: (a) any address on the Access policy + any admin's stolen ironics_session cookie = elevation as that admin (the roster is a shared second factor, not a personal one); (b) Epic-only accounts have no email to compare (accounts.ts:27 `email?: string` optional; Epic link writes playFabId, not email), so 'match the email' cannot even be attempted for the current owner if they signed in via Epic; (c) the Access roster becomes a hand-synced second list of who is an admin -- exactly the GTM 4.2 'two answers' the scope says it avoids.  
Fix: Add `stepUpSubject` (the Access `sub`, or the verified email as fallback) to the IronicsAdmins row, written at grant time by the owner (or captured on the admin's first successful elevate under a one-time 'bind' ceremony audited as admin.stepup_bound). The elevate Lambda refuses unless assertion.sub === row.stepUpSubject. 0.25 day. Then the Access policy can simply be 'everyone in the IdP' and the roster of record stays the DynamoDB row.

**4. [MINOR] Must-have 1 scope: 'Next route handler app/(console)/api/admin/elevate forwarding Cf-Access-Jwt-Assertion' with the Access application on ironics.org/admin/***  
Problem: App Router route groups do not appear in the URL: app/(console)/api/admin/elevate serves at /api/admin/elevate, which is NOT under /admin/*. Cloudflare's app-paths doc says only the configured path and its children fall under an application (protecting example.com/alpha 'does not cover example.com itself'), so the handler receives no Cf-Access-Jwt-Assertion header and the ceremony fails closed on first test -- or, if someone widens the Access app to the whole zone to make it work, every marketing visitor hits an Access login.  
Fix: Serve the handler under the protected prefix: app/(console)/admin/api/elevate/route.ts -> /admin/api/elevate (or add /api/admin/* as a second path on the same Access application). Add a test that the route path starts with /admin/.

**5. [MAJOR] Phase 0 / Must-have 4: 're-enable reservedConcurrency (-c reservedConcurrency=50)' and D5**  
Problem: api.ts:284-285,334 applies the context value to EVERY route function. 22 functions x 50 = 1,100 reserved, but AWS caps reservable at quota minus 100 ('You can reserve up to the Unreserved account concurrency value minus 100', Lambda concurrency doc fetched 2026-09-06) = 900 at the 1,000 quota. The deploy fails exactly as it did at quota 10. After this scope adds ~30 routes it would be 2,600. The stale-doc fix is right; the knob as written is not.  
Fix: Reserve per function at 5-10 (22 x 10 = 220), or reserve only on the unauthenticated public routes (Stats, EmailStart, EpicStart, BetaApply) where a spike originates, and leave admin/session routes unreserved. Add a synth-time test that sum(ReservedConcurrentExecutions) <= 900. 0.25 day.

**6. [MAJOR] today_baseline and Must-have 2 security baseline: 'audit table stays append-only at IAM', 'tamper-evident at IAM (Deny Update/Delete for AnyPrincipal)', proposed for bagman-money-journal too**  
Problem: Overclaimed. Live 2026-09-06: the resource policy denies UpdateItem/DeleteItem/BatchWriteItem only; `aws dynamodb delete-resource-policy --resource-arn .../IronicsAuditLog` removes it in one call by any principal with dynamodb:DeleteResourcePolicy (AdministratorAccess has it), then rows can be deleted; DeleteTable is not denied and IronicsAuditLog has DeletionProtectionEnabled=false (live); CloudFormation does not drift-detect resource policies (DynamoDB considerations doc), so a removed policy stays removed until the template changes; a PITR restore produces a new table on which the policy must be re-applied by hand. With zero CloudTrail (live) none of this leaves a record. 'Append-only' today means 'append-only for the Lambda roles', which is true and useful, but not the institutional claim being made.  
Fix: Say 'append-only for application principals; tamper-EVIDENT via CloudTrail' and make the evidence real: CloudTrail data events on IronicsAuditLog/IronicsAdmins/IronicsCounters (+ the journal) with alarms on DeleteResourcePolicy/PutResourcePolicy/DeleteTable/UpdateItem/DeleteItem from non-Lambda principals; deletionProtection on the audit table (Phase 0, already listed) and on the journal; make the S3 Object Lock (compliance mode) daily export of audit + journal NON-optional for the money tables -- it is the only WORM the account can have without Organizations SCPs (~$0.05/month). Keep PITR.

**7. [MAJOR] Must-have 2 E1 'dedicated bagman/admin/hmac ... so the portal stops holding the game-server earn key' and D12**  
Problem: E1 as scoped only moves the admin routes. api.ts:374-377 grants bagman/earn/hmac to `r.mints || r.resolves`, and grants.test.ts:284 pins EpicCallbackFn as a holder for /resolve-identity. That is the PUBLIC OAuth callback Lambda -- the most attacker-reachable function in the stack -- carrying the key that authorizes /escrow-entry, /settle-match, /refund-purchase, /purchase-bundle, /counted-entitlement, /earn. And the 'one key' is wider than the scope states: tentpole-stack.ts grants earnHmacSecret to 13 Lambdas including kill-telemetry (:1513) and rtc-token (:1873). After E1 the biggest transitive money principal in the portal is still there.  
Fix: Extend E1 to /resolve-identity: a read-only key (bagman/resolve/hmac or the admin key with actor='portal:epic-callback') accepted only by resolve-identity; drop bagman/earn/hmac from EpicCallbackFn and update grants.test.ts:284 so the earn key has ZERO portal holders. Same day of work as E1. Note the 13-Lambda blast radius in the doc so the later per-endpoint key allowlist is sized honestly.

**8. [MAJOR] Must-have 3 game-event hook: 'POST /v1/internal/game-event {playFabId, event} HMAC-signed by the tentpole' vs scope bullet 'HMAC-signed with the admin key'**  
Problem: If the tentpole signs the inbound hook with bagman/admin/hmac, the portal's game-event Lambda must hold that key to verify -- and a key that verifies can sign. An inbound, high-volume, internet-facing webhook Lambda (every first heartbeat / settle) would then be able to author /admin-adjust and /refund-purchase calls to the tentpole. That recreates the exact 'transitive money principal' E1 exists to remove, one hop over.  
Fix: A third, direction-specific secret bagman/portal-inbound/hmac ($0.40/month) held by the portal hook Lambda and the tentpole emitters only; it authorizes nothing on the tentpole. Add to grants.test.ts: no function holds both an inbound-verify key and an outbound-sign key. Reconcile the two contradictory sentences in the scope.

**9. [MAJOR] Must-have 2 O3 maker-checker adjustments, O4 holds, O5 escrow monitor actions, O8b/c KPIs + nightly reconciliation, TREASURER role, per-admin daily caps (28-39 days full / 22-29 lite)**  
Problem: Gold-plating for the population that exists: live IronicsAdmins=1, IronicsAccounts=1, IronicsAuditLog=3 rows, founders.issued=1, VOLTS scope 'no money moved' and nothing since. 'approver != proposer' is unsatisfiable with one human, and the same human holds admins:manage so can mint a second approver row to satisfy it (the scope's own D11 'interim rule' admits this). If thresholds live in SSM flags the owner edits, dual control is self-defeating. Holds have no enforcement point that matters (client calls PlayFab Client/PurchaseItem directly: AFLEconomyPersistenceSubsystem.cpp:434), the escrow 'release-held' action has no emitter (D20), the daily KPI row aggregates one wallet. O2 full journal edits all seven proven money Lambdas for a beta with zero volume, and 'written immediately after the PlayFab call' means a Lambda dying between the two writes silently drops a row -- so it is a shadow ledger reconciled nightly, not a 'ledger of record' (PlayFab remains balance of record).  
Fix: Cut Phase 3 to E1 + E2 + O1 (read-only inspector, audited) + the LITE journal + PlayStream->S3 export + drift alarm: ~9-13 days instead of 22-39. Ship the O3 proposal/approval STATE MACHINE only when a second human is on the roster; until then owner + fresh elevation + typed amount + hard cap + alarm. Thresholds and caps are code constants (deploy-gated with the grants tests), never SSM flags. Rename the journal honestly ('shadow ledger; PlayFab is balance of record; nightly reconciliation is the control'). Move O4/O5-actions/O8b-c to Phase 4 gated on real staked volume and on D20.

**10. [MINOR] Must-have 1 role/permission design: 18 permissions, 4 roles incl. TREASURER, audit GSIs x2, request-metadata drawer, owner-only CSV export, admin.roles_changed, INVITED state**  
Problem: For a roster of one person and an audit table holding 3 rows, this is the six-role taxonomy the scope rejects, wearing different clothes. Permission-as-primitive is cheap, but 18 named permissions, a role nobody holds, two GSIs and an export format are specification debt that must be mocked (doctrine 7), tested and maintained before anyone but the operator logs in.  
Fix: Ship BPD s12's viewer/operator/owner literally (money inside owner until a second human exists), ~8 permissions (accounts:read/approve/ban, admins:manage, economy:mint, release:write, flags:write, audit:read), `requires` on RouteSpec + the two tests. Defer treasurer, GSIs, CSV export and the metadata drawer to the day a second admin is granted (that audit row is the trigger). Saves ~3-4 days of the Phase 1 MVP.

**11. [MINOR] today_baseline 'IronicsAdmins scan Count=1 ... the operator, 2026-08-25' and Phase 1 'confirm 01M06WNV71GP2QWYPBQA5JT4WC is the initial owner'**  
Problem: Verified live (Count=1, deletionProtection=true) -- the fact holds. But the scope treats the single seed row as the migration target (`roles={owner}`) with no independent check that this accountId is the operator's Epic-linked account rather than the email-only test account created during the 08-24 build session; a wrong owner row is unrecoverable through the console once the seed script refuses to run and revoke-last-owner is blocked by the scope's own ConditionExpression.

**12. [MINOR] Must-have 3 'Cloudflare Web Analytics switched on for ironics.org (free, cookieless, no consent change)'**

**13. [MINOR] Must-have 3 Accounts list: 'search by accountId/email/Epic sub/PlayFabId' with accounts:read granted to VIEWER**  
Problem: Viewer/analyst gets raw email, Epic subject and PlayFabId for every tester -- more PII than the wallet view, which the scope carefully masks. GTM section 8's PII inventory treats these as the identifiers to minimise, and a read view with no audit row is the one surface an insider can scrape without trace.

**14. [MINOR] Must-have 3 scope: 'analytics-server.ts forwarder (Worker -> /v1/internal/events or direct PutItem via a signed route)' vs security baseline 'the Worker forwards a per-user Access assertion, never a shared secret'**

**15. [MINOR] Architecture constraint the scope never states: one Lambda per route (api.ts:324-396) x ~30 new routes**  
Problem: Live template = 179 resources; each route costs 7 (Function, Role, Policy, LogGroup, Permission, Integration, Route). The scope adds ~30 routes (+210), 3-4 tables, a roll-up Lambda, ~20 alarms/metric filters, SNS, CloudTrail -> ~440-460 of CloudFormation's hard 500-resource cap (quotas doc fetched 2026-09-06). Every route after that fails the deploy, and 50+ NodejsFunctions also means 50 esbuild bundles per `cdk deploy` and 50 cold-start surfaces for a console polled by one person.  
Fix: Decide the shape before Phase 1: either a nested AdminApiStack (keeps the per-route IAM tests intact) or one Lambda per domain (accounts/economy/releases) with internal dispatch and a per-domain grant set (breaks the per-route grants tests -- so prefer the nested stack). Add a synth-time assertion that Resources < 450.

**16. [MINOR] Must-have 1 'Cloudflare Access ... Independent MFA (security key, fallback TOTP) ... Zero Trust free <= 50 users' and D3**

If OTP + Independent MFA is not supported, the step-up degrades to email-OTP-only, which is weaker than the game's own Epic 2FA.  
Fix: Before ruling D3, the operator creates the Zero Trust team and configures a test self-hosted app with OTP + Independent MFA and screenshots the prompt (30 minutes). If unsupported, add GitHub/Google as the Access IdP for the roster (still $0) or take the WebAuthn-in-Lambda alternative. Cite the seat count from the dashboard, not a summary.

**17. [MINOR] Must-have 3 flags: 'PUT /v1/admin/flags ... FlexMatch cells (the existing SSM param, now edited from /admin)' and D27**  
Problem: ironics-portal-stack.ts:13-16 makes 'shares no construct, no table and no function' with BagManTentpoleStack a design invariant; a portal Lambda with ssm:PutParameter on /bagman/matchmaking/flexmatch-cells is the first portal->tentpole WRITE path, and create-ticket's last-known-good cache means a bad write from the console is served for the cache TTL with no rollback lever in the same screen.

Problem: The existing limiter `consumeRateLimit` fails OPEN by design (api.ts:134-137: 'fails open on any error that is not a condition failure, deliberately'). ### Missing from the first draft (15)

- IAM credential hygiene as the actual Phase 0 gate: deny-all-unless-MFA on group IRONICS, rotation of the 86-day access key ***REMOVED-AWS-KEY-ID (rotated; see Secrets Manager)***, removal of the 10 unrelated managed policies (Amplify/Beanstalk/Vercel/AIDevOps*) from the only human principal, and a named path to short-lived credentials (IAM Identity Center, $0). The scope's 'MFA device' item protects the console login, not the key every script and `cdk deploy` uses.
- Detection on the privileged control plane, not just the data tables: CloudTrail metric-filter alarms on kms:Sign from non-Lambda principals (the session key policy is root kms:* -- any admin principal can forge a session or elevation JWT), lambda:UpdateFunctionCode on money functions, secretsmanager:GetSecretValue on bagman/playfab/secret and bagman/earn/hmac outside their granted roles, and dynamodb:DeleteResourcePolicy/PutResourcePolicy/DeleteTable.
